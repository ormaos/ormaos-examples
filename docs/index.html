First, by hand

The job, and reading a recording

A scheduled Python job prints sync finished: OK, exits without an error, and in the morning the stock of some products is wrong. The run cannot be repeated and nothing was logged, so whoever investigates, a person or a coding agent, has only the code and the data that is left.

Here is the demo job, order-sync, in a fresh copy: install Ormaos, record one run, then read the recording.

order-sync

A real terminal session, not edited. Pauses are shortened during playback. The summary names an exception that was caught and never seen; the next commands show where it was raised and handled, the calls below the handler, and the I/O they did.

Test 1

An agent, without and with the recording

The same job on the morning after a night run that cannot be repeated. A coding agent gets the folder and one sentence: the run said OK, some products have wrong stock, find out why. On one side the folder has last night's recording, on the other it has not.

runs with the recording stated the cause as proven
5 of 5
runs without the recording stated the cause as proven
0 of 5

Measured: N = 5 runs per side, model claude-opus-5-5, each run started with only the prompt, in a sandbox that holds only its own folder.

On both sides, every run named the except that skips orders and the orders that were skipped. The difference is the reason for the skips. With the recording, the answer gave the exception type, how many times it was raised, and the lines where it was raised and handled, as what happened last night. Without it, every answer said the reason could not be confirmed and left other causes open.

On neither side could a run say what exactly was wrong in the text of the rejected values: Ormaos records shapes (types, lengths, structure), never values.

Test 2

A second job, two nights compared

Another job, freight-quote, asks a carrier's API for the freight of tomorrow's shipments and writes the quotes to a database. Last night it printed quotes finished: OK, and this morning 17 of its 26 quotes are lower than what the carrier charged. The night before was fine, and its quotes are gone: each run replaces them. Both nights were recorded, and ormaos diff says what the second one did that the first did not.

freight-quote

A real terminal session, not edited. In the second night, 17 of the 26 calls to the carrier were answered with 429, 17 urllib.error.HTTPError were caught at job.py:43, and rate in ratecard.py ran 17 times. In the first night, none of the three.

The same session as text

The same comparison as in the first test, on this job: on one side the folder has the recordings of the two nights, on the other it has not.

runs with the recordings gave the carrier's 429 as what happened
5 of 5
runs without the recordings gave the carrier's 429 as what happened
0 of 5

Measured: N = 5 runs per side, model claude-opus-5-5, each run started with only the prompt, in a sandbox that holds only its own folder.

On both sides, every run named the except that prices a shipment from an older rate card when the call to the carrier fails, and the 17 quotes that are equal to that rate card. Without the recordings, all five runs produced a 429 themselves on a copy, named a used-up daily allowance of calls as the most likely reason, and said they could not confirm which error it was last night. With the recordings, all five gave it as what happened: 9 calls answered with 200, 17 with 429, and 17 exceptions caught at job.py:43.

Test 3

Eight bugs, three ways in

A larger measurement, agent-bench: eight small scheduled jobs, each with one bug of a different kind, each printing its OK line on the bad night. A coding agent gets the code, the data that night left and the symptom, and is asked to find the cause and fix it: with nothing more (none), with a VizTracer trace of the bad night (raw), or with its Ormaos recording (ormaos). A hidden check then decides whether the code it left is fixed.

Measured: N = 24 runs per arm (8 bugs, 3 runs each), model claude-opus-5-5, the first attempt of every run counted. The interval is the 95% Wilson score interval; tokens include cache tokens, as the command line reports them.

At this size the difference is within the margin. The four runs that were not fixed had found the cause, but changed the job's last line, which the check reads as cron does. Looked at after the results, not planned: counted as fixed, those four would make every arm 24/24, so this benchmark does not separate the arms. The bugs were written for this benchmark by the people who make Ormaos. The report has every run, per bug, with what the check said.

By kind of program

Seven kinds of program, one question each

Seven small programs in use-cases, one per kind of developer. Each prints one ordinary line, and in each execution something happened that the line does not say. Below, for each: the question, one command on the recording, and what it printed. Ormaos shows what happened; whether it is what should have happened is for the reader to decide.

Each folder also has a questions.json: 48 factual questions over the 7 executions, each with its answer computed from a second execution of the same program without Ormaos, under sys.settrace, and never from the recording. Every answer was the same in 3 runs.

Web backend

The program prints GET /customers/3/orders -> 200, 12 orders. Which queries did that one request run, how many times each, and from which lines?

Data pipeline

The program prints report.csv written: 4 regions. How many rows went into the merge, and how many came out?

Notebook

The last cell prints a total. In the session that printed it, which step had the rows second, and how many rows? Each record() block is one recording, numbered in the order the blocks ran: r2 is the second.

ML training

The program prints trained 40 steps and a loss. Was there a NaN in a tensor during the run, and where was the first one?

RL environment

The program prints the mean return of 20 episodes. Inside one step, was the reward computed before the move or after it?

AI app

The program prints 8 tickets summarized. How many requests went to each model, and what was each answered?

A change made by an agent

A coding agent was asked for a discount on invoices. The program prints the same line before and after its change. What does the execution do after the change that it did not do before?

Run it yourself

Each block is the whole scenario. They need Python 3.12 or newer and git, on Linux; Ormaos is installed from GitHub into a virtual environment of the folder, nowhere else.

The seven kinds of program

Each scenario.py copies its program to a new folder, records it, and prints every question with its answer and the command shown above with its output. The other six are the same with their folder name; four have a requirements.txt, three need only the standard library.

Not yet

What Ormaos does not have today. What is needed to install it, and everything else, is in the guide and the README.

  • A package on PyPI. Install from GitHub.
  • A stable file format. Today's is provisional.
  • Windows and macOS: not tested.
  • Reading commands for a folder other than ./.ormaos.
  • Line-by-line reading for tree, exceptions, io, path and diff.
  • A way to know which signal ended a process that nothing waited for.
  • Web servers that start worker processes (uvicorn, gunicorn) in the compatibility matrix.
